# WBE 上线与环境搭建手册

## 1. 手册适用范围

本手册覆盖污水信息因子数据库的三个运行层：

- 前端：`wbe-ui`，Vue 3 + TypeScript + Vite，生产制品是静态 `dist` 压缩包。
- 后端：`wbe-backup`，Spring Boot + Java 21，生产制品是可执行 JAR。
- 数据库：MySQL 8.4，数据保存在 Docker volume，不跟随前后端版本目录替换。

当前测试服务器采用“本地构建制品 → SHA-256 校验 → 服务器版本目录 → `current` 软链接原子切换”。不在服务器上临时修源码，不在普通前端发布中重建数据库。

## 2. 当前部署架构

```text
浏览器
  → Nginx（静态前端、SPA 回退、/API 代理）
  → Spring Boot 8080（仅 Docker 私网）
  → MySQL 3306 + Redis 6379（均不对公网暴露）
```

服务器关键目录：

```text
/opt/wbe/
├── .env                         # 真实密码，0600，不入 Git
├── compose.artifact.yaml         # 容器编排
├── deploy/runtime/               # 固定 Nginx/JRE 运行时
├── scripts/deploy/               # 发布与回滚脚本
├── incoming/<version>/           # 待校验上传区
├── releases/<version>/           # 不可变版本目录
├── current -> releases/<version> # 当前代码版本
├── map-current -> maps/<version> # 独立地图版本
├── backups/mysql/                # 数据库备份
└── .deploy-records/               # 发布日志与成功状态
```

这个结构的目的是：上传未完成时不影响线上；发布失败可回到旧版本；前端发布不重启后端；代码回滚不覆盖 MySQL volume。

## 3. 已搭好环境的日常上线

### 3.1 定义本次发布变量

```bash
PROJECT_ROOT='/Users/licong/Downloads/project/污水管理系统'
UI_DIR="$PROJECT_ROOT/wbe-ui"
BACKEND_DIR="$PROJECT_ROOT/wbe-backup"
SSH_KEY='/Users/licong/.ssh/wbe_aliyun_test'
SERVER='admin@8.210.92.75'
VERSION="code-$(date '+%Y%m%d-%H%M%S')"
```

- `PROJECT_ROOT`：固定项目根目录，避免在错误仓库构建。
- `UI_DIR` / `BACKEND_DIR`：将前后端分开验证。
- `SSH_KEY`：显式使用项目私钥，私钥永远不复制进仓库。
- `SERVER`：固定当前测试服务器。
- `VERSION`：每次都用新名称，不覆盖旧版本，使回滚可追溯。

### 3.2 选择正确的发布类型

| 变更 | 构建 | 发布脚本 | 是否重启后端 | 是否先备份数据库 |
| --- | --- | --- | --- | --- |
| 仅 `wbe-ui` | `--frontend-only` | `deploy-frontend.sh` | 否 | 通常否 |
| 仅 `wbe-backup` | `--backend-only` | `deploy-backend.sh` | 是 | 是 |
| 前后端都改 | 默认双端 | `deploy-code.sh` | 是 | 是 |
| PMTiles/字体/sprite/区域索引 | `--with-map` | `deploy-map.sh` | 否 | 否 |
| SQL 或启动建表逻辑 | 后端制品 | 后端或双端 | 是 | **必须** |

选错发布类型的主要风险是：前端脚本不会替换新 JAR；双端脚本会重启后端；地图大文件不应混入普通前端包。

### 3.3 发布前只读检查

```bash
git -C "$UI_DIR" status -sb
git -C "$BACKEND_DIR" status -sb
git -C "$UI_DIR" fetch --prune origin
git -C "$BACKEND_DIR" fetch --prune origin
bash -n "$PROJECT_ROOT"/scripts/deploy/*.sh
ssh -i "$SSH_KEY" -o IdentitiesOnly=yes -o BatchMode=yes \
  -o StrictHostKeyChecking=yes "$SERVER" \
  'readlink -f /opt/wbe/current; sudo docker compose -f /opt/wbe/compose.artifact.yaml ps'
```

- `status -sb`：确认将被构建的工作区和分支。
- `fetch --prune`：更新远端引用并清理已删除远端分支，不改动本地文件。
- `bash -n`：只做 Shell 语法检查，不执行发布。
- `readlink -f`：记录当前回滚点。
- `docker compose ps`：发布前若已有容器不健康，应先处理故障，不能用新版本掩盖。

### 3.4 前端验证

```bash
cd "$UI_DIR"
npm ci
npm run test:unit -- --run
npm run build
git diff --check
```

- `npm ci`：严格按 `package-lock.json` 重建依赖，不自动升级。
- `test:unit -- --run`：单次执行全部单元和组件测试。
- `npm run build`：同时运行 Vue/TypeScript 类型检查、Vite 构建和生产数据源检查。
- `git diff --check`：阻止冲突标记、错误空格和行尾问题进入制品。

### 3.5 后端验证

```bash
cd "$BACKEND_DIR"
./mvnw clean test package
git diff --check
```

- Maven Wrapper 固定项目 Maven 版本，不依赖服务器全局 Maven。
- `clean`：先移除旧 `target`，避免把上次编译结果当成本次产物。
- `test`：运行后端契约、数据库、控制器和服务测试。
- `package`：生成真实上传的 JAR。

### 3.6 数据库发布前备份

只有后端重启或 schema initializer 变更时才需要执行；纯前端发布不必扰动数据库。

```bash
ssh -i "$SSH_KEY" -o IdentitiesOnly=yes -o BatchMode=yes \
  -o StrictHostKeyChecking=yes "$SERVER" '
    set -e
    stamp=$(date +%Y%m%d-%H%M%S)
    file=/opt/wbe/backups/mysql/wbe-before-$stamp.sql.gz
    sudo install -d -m 0700 /opt/wbe/backups/mysql
    sudo docker exec wbe-local-mysql-1 sh -c '\''
      exec mysqldump -uroot -p"$MYSQL_ROOT_PASSWORD" \
        --single-transaction --quick --hex-blob --routines --events --triggers \
        --set-gtid-purged=OFF --no-tablespaces "$MYSQL_DATABASE"
    '\'' | gzip | sudo tee "$file" >/dev/null
    sudo test -s "$file"
    sudo gzip -t "$file"
    echo "$file"
  '
```

- `--single-transaction`：对 InnoDB 产生一致性快照，减少锁表时间。
- `--quick`：逐行读取，避免大表整体进内存。
- `--routines --events --triggers`：除表数据外同时保留数据库行为。
- `test -s`：确认备份不是空文件。
- `gzip -t`：确认压缩流没有损坏。

### 3.7 构建制品

```bash
cd "$PROJECT_ROOT"

# 仅前端
bash scripts/deploy/build-artifacts.sh --frontend-only

# 仅后端
bash scripts/deploy/build-artifacts.sh --backend-only

# 前后端
bash scripts/deploy/build-artifacts.sh
```

三条命令三选一。脚本会使用两个 Git 短 SHA 和时间生成 `release/<version>`，同时生成 SHA-256 清单。已经在完全相同的代码状态下运行全部测试时，可追加 `--skip-tests`，但不能用它跳过尚未做过的验证。

### 3.8 上传和校验

```bash
RELEASE_DIR="$PROJECT_ROOT/release/<实际制品目录>"
VERSION='<本次唯一版本名>'

ssh -i "$SSH_KEY" -o IdentitiesOnly=yes -o BatchMode=yes \
  -o StrictHostKeyChecking=yes "$SERVER" \
  "sudo install -d -m 0755 -o admin -g admin /opt/wbe/incoming/$VERSION"

scp -O -i "$SSH_KEY" -o IdentitiesOnly=yes -o BatchMode=yes \
  -o StrictHostKeyChecking=yes \
  "$RELEASE_DIR"/* "$SERVER:/opt/wbe/incoming/$VERSION/"

ssh -i "$SSH_KEY" -o IdentitiesOnly=yes -o BatchMode=yes \
  -o StrictHostKeyChecking=yes "$SERVER" \
  "cd /opt/wbe/incoming/$VERSION && \
   [ ! -f FRONTEND_SHA256SUMS ] || sha256sum -c FRONTEND_SHA256SUMS; \
   [ ! -f BACKEND_SHA256SUMS ] || sha256sum -c BACKEND_SHA256SUMS"
```

- `install -d`：创建权限明确的新接收目录，不覆盖旧包。
- `scp -O`：使用已在该服务器验证过的 SCP 兼容模式传输。
- `sha256sum -c`：服务器以本地构建时的清单验证传输完整性；校验失败不得解包。

### 3.9 执行切换

仅前端：

```bash
sudo /opt/wbe/scripts/deploy/deploy-frontend.sh \
  /opt/wbe/incoming/$VERSION/<frontend.tar.gz> \
  /opt/wbe/incoming/$VERSION/FRONTEND_SHA256SUMS \
  "$VERSION"
```

仅后端：

```bash
sudo /opt/wbe/scripts/deploy/deploy-backend.sh \
  /opt/wbe/incoming/$VERSION/<backend.jar> \
  /opt/wbe/incoming/$VERSION/BACKEND_SHA256SUMS \
  "$VERSION"
```

前后端：

```bash
sudo /opt/wbe/scripts/deploy/deploy-code.sh \
  /opt/wbe/incoming/$VERSION/<frontend.tar.gz> \
  /opt/wbe/incoming/$VERSION/<backend.jar> \
  /opt/wbe/incoming/$VERSION/CODE_SHA256SUMS \
  "$VERSION"
```

发布脚本会再次校验制品，拒绝不安全的 tar 路径，创建新 release，切换 `current`，按需重建后端/Nginx，等待健康检查，然后写入 `.deploy-records`。

### 3.10 上线后验收

```bash
curl -fsS http://8.210.92.75/ >/dev/null
curl -fsS http://8.210.92.75/map-visualization >/dev/null
curl -fsS http://8.210.92.75/icd11-sankey >/dev/null

ssh -i "$SSH_KEY" -o IdentitiesOnly=yes -o BatchMode=yes \

```

页面检查证明 Nginx/SPA 可用，API 检查证明 Nginx 代理、后端和数据库整条链路可用。容器必须全部为 `healthy`，且 `current` 指向本次版本。

### 3.11 回滚

```bash
sudo /opt/wbe/scripts/deploy/rollback.sh code <上一个健康版本名>
```

回滚只切换前后端制品。如果新后端已执行向前兼容的增量建表，通常无需恢复数据库；如确实需要恢复，必须单独进入维护窗口，不能把 SQL 恢复夹在普通代码回滚里。

## 4. 数据库连接和操作

### 4.1 生产环境如何连接

Spring Boot 不使用宿主机 `localhost:3306`，而是通过 Docker 网络使用服务名：

```text
DB_URL=jdbc:mysql://mysql:3306/wbe?...
DB_USERNAME=<来自 /opt/wbe/.env>
DB_PASSWORD=<来自 /opt/wbe/.env>
```

`mysql` 是 Compose service name，只在 `wbe_private` 私网可解析。MySQL 没有 `ports:` 映射，这样公网不能直接扫描 3306。

### 4.2 只读检查

```bash
sudo docker exec wbe-local-mysql-1 sh -c '
  MYSQL_PWD="$MYSQL_ROOT_PASSWORD" mysql -uroot "$MYSQL_DATABASE" \
    --batch --skip-column-names \
    -e "SELECT COUNT(*) FROM information_schema.tables WHERE table_schema=DATABASE();"
'
```

`docker exec` 在 MySQL 容器内执行客户端，密码只从容器环境读取，不回显到命令行参数。`--batch --skip-column-names` 便于自动验收准确解析单个结果。

### 4.3 恢复原则

项目的 `mysql-restore.sh` 只允许恢复到空库，并要求显式设置 `CONFIRM_DATABASE`，这是为了防止误覆盖现网数据。

```bash
cd /opt/wbe
CONFIRM_DATABASE=wbe scripts/docker/mysql-restore.sh \
  /opt/wbe/backups/mysql/<backup.sql.gz>
```

如目标库已有表，脚本会拒绝执行。真实灾难恢复应新建空库或新 MySQL volume，验证备份后再切换，不直接清空正在运行的生产库。

## 5. 从零搭建新环境

### 5.1 服务器和账号

以 Ubuntu LTS 为例，先用云厂商提供的 root 通道登录，再创建日常发布用户：

```bash
sudo adduser wbeadmin
sudo usermod -aG sudo wbeadmin
sudo install -d -m 0700 -o wbeadmin -g wbeadmin /home/wbeadmin/.ssh
sudo install -m 0600 -o wbeadmin -g wbeadmin /tmp/authorized_keys \
  /home/wbeadmin/.ssh/authorized_keys
```

- 不日常使用 root，可以减少误操作范围。
- `.ssh` 要求 0700，`authorized_keys` 要求 0600，否则 SSH 可能因权限过宽而拒绝密钥。
- 先在新终端确认 `ssh wbeadmin@<ip>` 成功，再考虑禁用 root 远程登录。

### 5.2 基础软件和 Docker

```bash
sudo apt update
sudo apt install -y ca-certificates curl openssl rsync tar gzip
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg \
  -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc
. /etc/os-release
echo "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.asc] \
https://download.docker.com/linux/ubuntu $VERSION_CODENAME stable" \
  | sudo tee /etc/apt/sources.list.d/docker.list >/dev/null
sudo apt update
sudo apt install -y docker-ce docker-ce-cli containerd.io \
  docker-buildx-plugin docker-compose-plugin
sudo systemctl enable --now docker
sudo docker version
sudo docker compose version
```

- 第一次 `apt update` 获取系统当前索引。
- Docker GPG key 用于验证官方仓库包签名。
- `dpkg --print-architecture` 和 `$VERSION_CODENAME` 自动选择当前 CPU/Ubuntu 版本，不硬编码。
- `enable --now`同时立即启动 Docker 并设置开机自启。

### 5.3 创建运维目录

```bash
sudo install -d -m 0755 \
  /opt/wbe/deploy/runtime/java \
  /opt/wbe/deploy/runtime/nginx \
  /opt/wbe/deploy/caddy \
  /opt/wbe/scripts/deploy \
  /opt/wbe/scripts/docker \
  /opt/wbe/incoming \
  /opt/wbe/releases \
  /opt/wbe/maps \
  /opt/wbe/backups/mysql \
  /opt/wbe/.deploy-records
sudo chown -R wbeadmin:wbeadmin /opt/wbe/incoming /opt/wbe/backups
```

`运行配置` 和 `版本目录` 分开；日常用户只需写入 incoming/backups，发布切换仍经过 `sudo` 脚本。

### 5.4 安装配置和生成密码

从受控部署包复制以下文件到 `/opt/wbe`：

```text
compose.artifact.yaml
deploy/runtime/
deploy/caddy/
scripts/deploy/
scripts/docker/
.env.artifact.example
```

然后生成真实环境文件：

```bash
cd /opt/wbe
cp .env.artifact.example .env
chmod 0600 .env
openssl rand -hex 32
openssl rand -hex 32
openssl rand -hex 32
```

三次随机值分别用于 `MYSQL_PASSWORD`、`MYSQL_ROOT_PASSWORD`、`REDIS_PASSWORD`。手工写入 `.env`，不把真实值粘贴到文档、Shell 历史或 Git。同时设置 `HTTP_BIND_ADDRESS`、`HTTP_PORT`、`APP_DOMAIN` 和 `CORS_ALLOWED_ORIGINS`。

```bash
sudo docker compose --env-file /opt/wbe/.env \
  -f /opt/wbe/compose.artifact.yaml config --quiet
```

`config --quiet` 只解析和校验 Compose，能在启动前发现缺少密码、变量或 YAML 错误。

### 5.5 构建固定运行时

```bash
cd /opt/wbe
sudo docker compose --env-file .env -f compose.artifact.yaml build backend nginx
```

这一步只构建 JRE 21 和 Nginx 运行容器，不把业务 JAR 或前端代码烧进镜像。以后正常发布只替换挂载制品，无需重建镜像。

### 5.6 准备第一个代码版本

在开发机按 3.4–3.8 构建并上传前后端制品，然后执行 `deploy-code.sh`。首次发布前必须准备 `map-current`；若没有地图包，Nginx 的独立地图挂载会失败。

```bash
cd "$PROJECT_ROOT"
bash scripts/deploy/build-artifacts.sh --with-map
```

`--with-map` 只在首次部署或地图资源确实改变时使用，因为 PMTiles 包大且与普通前端回滚周期不同。

### 5.7 初始化数据库

两种方式只能选一种：

1. **全新空库**：先启动 MySQL/Redis/Mailpit，再启动后端。Spring SQL schema 和项目的幂等 schema initializer 创建所需结构。
2. **迁移旧数据**：先只启动 MySQL，把已验证的单库备份恢复到空库，再启动新后端执行增量 schema initializer。

```bash
cd /opt/wbe
sudo docker compose --env-file .env -f compose.artifact.yaml up -d mysql redis mailpit
sudo docker compose --env-file .env -f compose.artifact.yaml ps
```

若是迁移，此时使用 4.3 的空库恢复流程。恢复后再发布后端，并关注日志中的 schema 初始化错误。

### 5.8 启动和首次验收

```bash
cd /opt/wbe
sudo docker compose --env-file .env -f compose.artifact.yaml up -d backend nginx
sudo docker compose --env-file .env -f compose.artifact.yaml ps
sudo docker compose --env-file .env -f compose.artifact.yaml logs --tail=200 backend
curl -fsS http://127.0.0.1:${HTTP_PORT:-8088}/api/home/overview
```

先启动后端，因为 Nginx 声明依赖后端健康。`logs --tail=200` 用于确认数据库增量结构、Redis 和应用都成功。最后的 API 检查验证了 Nginx → Spring Boot → MySQL 整条链路。

## 6. Git 提交与发布的顺序

1. 先拉取远端引用并检查本地分支没有分叉。
2. 只清理明确未被引用的临时或原型文件。
3. 前后端分别运行全量测试。
4. 使用中文提交信息提交，并推送当前功能分支。
5. 使用已提交 SHA 构建制品，保证仓库可重现线上内容。
6. 涉及后端/schema 时先备份 MySQL。
7. 发布、健康检查、API 验收，并记录新旧版本和制品 SHA-256。

标准提交命令：

```bash
git status --short
git diff --check
git add -A
git diff --cached --check
git commit -m '优化首页与桑基图交互并完善部署文档'
git push origin "$(git branch --show-current)"
```

`git add -A` 会同时记录新增、修改和删除，所以必须在此前阅读 `status`。`diff --cached --check` 针对真正将提交的内容做最后检查。`push` 显式指定当前分支，不意外推送其他本地分支。

## 7. 常见故障定位

| 现象 | 先检查 | 原因 |
| --- | --- | --- |
| 首页 502 | `docker compose ps` 和 backend 日志 | Nginx 连不到后端 |
| 前端页面旧 | `readlink -f /opt/wbe/current` 和 `index.html` hash | 软链接未切换或浏览器缓存 |
| 后端健康超时 | backend 日志、MySQL/Redis 健康 | 配置缺失、schema 失败或依赖不可用 |
| 数据加载不出 | `/api/home/overview` 直接请求 | 区分前端渲染问题与 API/数据问题 |
| 制品校验失败 | 本地/服务器 SHA-256 | 上传不完整或清单与包混用 |
| MySQL 无法恢复 | 目标库表数和 `CONFIRM_DATABASE` | 安全脚本故意拒绝覆盖非空库 |
